## 2. Найденные дефекты

Во всех шагах остальные поля заполнены корректно.

### BUG-01. На сегодняшнюю дату можно забронировать уже прошедшее время — приоритет высокий

- **Условия:** текущее время позже 10:00.
- **Шаги:** «Дата» — сегодня; «Начало» — 09:00; «Окончание» — 10:00; нажать «Забронировать».
- **Ожидаемый результат:** ошибка, бронь не создаётся. ТЗ: «для текущего дня нельзя выбрать прошедшее время».
- **Фактический результат:** «Бронирование создано. Средняя, <сегодня>, 09:00–10:00 · Анна Смирнова». Так же принимается слот, который уже начался: при 12:00 проходит 11:30–12:30.
- **Обоснование приоритета:** несоответствие ТЗ («для текущего дня нельзя выбрать прошедшее время»); бронирование «задним числом» неприемлемо.
- **Автотест:** `test_discovered_defect` (xfail, strict).

### BUG-02. Длительность встречи не проверяется, допускается окончание, равное началу — приоритет высокий

- **Шаги:** дата в будущем; по очереди попробовать интервалы 10:00–10:00, 10:00–10:29, 10:00–14:01 и 09:00–18:00.
- **Ожидаемый результат:** ошибка во всех четырёх случаях. ТЗ: «время окончания позже начала, длительность от 30 минут до 4 часов».
- **Фактический результат:** во всех случаях «Бронирование создано». Отклоняется только окончание раньше начала.
- **Обоснование приоритета:** несоответствие ТЗ («окончание позже начала», «длительность от 30 минут до 4 часов»); принимаются брони на 0 минут и на 9 часов.

### BUG-03. HTML в поле «Ваше имя» исполняется в сообщении об успехе (XSS) — приоритет средний

- **Шаги:** в «Ваше имя» ввести `<img src=x onerror="alert(1)">`; нажать «Забронировать».
- **Ожидаемый результат:** имя показано как текст, код не выполняется.
- **Фактический результат:** открывается `alert(1)`: введённая разметка выполняется как код страницы.
- **Обоснование приоритета:** уязвимость XSS; затрагивает только того, кто ввёл код, — данные не отправляются и не сохраняются.

### BUG-04. Принимается дробное число участников — приоритет низкий

- **Шаги:** «Участники» — `2.5`; нажать «Забронировать».
- **Ожидаемый результат:** ошибка: количество участников должно быть целым числом от 1 до 20.
- **Фактический результат:** «Бронирование создано».
- **Обоснование приоритета:** количество участников должно быть целым; правило вместимости не нарушается.

### BUG-05. Проверка почты пропускает некорректные адреса — приоритет низкий

- **Шаги:** в «Рабочая почта» по очереди ввести `a@@b.c`, `a,b@c.d`, `a@b.c.`; нажать «Забронировать».
- **Ожидаемый результат:** «Введите корректную рабочую почту.» ТЗ: «электронная почта имеет корректный формат».
- **Фактический результат:** все три адреса приняты.
- **Обоснование приоритета:** несоответствие ТЗ («корректный формат почты»); очевидно неверные адреса (`abc`, `a@b`) отклоняются.

### Замечания

- **З-1.** Текст ошибки вместимости не согласован с числом: «В комнате максимум 10 участника».
- **З-2.** После смены комнаты ошибка вместимости для прежней комнаты остаётся до повторной отправки формы.
- **З-3.** Если после успешной брони изменить поля, на экране остаётся «Бронирование создано» со старыми данными.
- **З-4.** В сообщении дата выводится в формате ISO (`2030-06-17`), а в поле ввода — ДД.ММ.ГГГГ.

## 3. Автотесты (Python + Playwright)

Тесты — [tests/test_booking.py](tests/test_booking.py), Page Object формы — [pages/booking_page.py](pages/booking_page.py).

| Тест | Тип | Пункт чек-листа | Что проверяет |
|---|---|---|---|
| `test_successful_booking` | Позитивный | CL-02 | Бронь на будущую дату: сообщение содержит комнату, дату, время и имя; ошибок у полей нет |
| `test_invalid_booking` | Негативный | CL-04 | Вчерашняя дата: ошибка «Дата не может быть в прошлом.» |
| `test_discovered_defect` | Дефект BUG-01 | CL-05 | Сегодня, слот 09:00–10:00 при текущем 12:00 должен быть отклонён |

**Решения:**
- Page Object: `BookingPage` содержит локаторы и действия (`open`, `fill`, `submit`, `book`, `error`), данные брони — dataclass `Booking`, варианты собираются через `replace(VALID, ...)`. Проверки — только в тестах.
- «Сейчас» в браузере зафиксировано на 14.06.2030 12:00 в часовом поясе `Europe/Moscow` (`page.clock`). Результат не зависит от даты, времени и часового пояса запуска.
- Тест дефекта помечен `xfail(strict=True, raises=AssertionError)`. После исправления BUG-01 он упадёт с `XPASS(strict)`. Ошибки окружения не маскируются под дефект.
- Локаторы — по подписям полей и ролям (`get_by_label`, `get_by_role`).

### Как запускать

**Docker** (нужен Docker с Compose v2), из корня репозитория:

```bash
docker compose run --build --rm tests
```

**Без Docker** (Python 3.12):

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements.txt
python -m playwright install chromium
python -m pytest
```

| Задача | Команда |
|---|---|
| Только тесты бронирования | `python -m pytest tests/test_booking.py -v` |
| Один тест | `python -m pytest -k defect` |
| С видимым браузером | `python -m pytest --headed --slowmo 500` |
| Другой стенд | `python -m pytest --base-url <URL>` или `BASE_URL=<URL> docker compose run --build --rm tests` |

**Результаты:** `artifacts/junit.xml` — отчёт о прогоне; `artifacts/browser/` — трассировка и скриншоты упавших тестов.

**Как читать результат:**
- `3 passed, 1 xfailed` — ожидаемый итог;
- `XPASS(strict)` у `test_discovered_defect` — BUG-01 исправлен, нужно снять `xfail`;
- `FAILED` или `ERROR` — регрессия или проблема окружения.

## 4. Вопросы, допущения, проверенные области, риски и ограничения

### Вопросы к требованиям

**Дата и время**
- **В-1.** По какому часовому поясу определяются «сегодня» и «прошедшее время»: по браузеру пользователя или по офису?
- **В-2.** Можно ли начать встречу в текущую минуту, или нужен запас? Есть ли сетка слотов (кратность 15 или 30 минут)?
- **В-3.** Границы длительности включаются: ровно 30 минут и ровно 4 часа допустимы?
- **В-4.** Может ли встреча переходить через полночь? Сейчас интервал 23:30–00:30 отклоняется.
- **В-5.** Есть ли рабочие часы офиса? Можно ли бронировать на выходные и праздники?
- **В-6.** На сколько вперёд можно бронировать? Сейчас принимается даже 2099 год.
- **В-7.** Если страница открыта до полуночи, а форма отправлена после, должна ли «сегодняшняя» дата обновляться без перезагрузки?

**Комнаты и участники**
- **В-8.** Нужно ли проверять занятость комнаты (пересечения с другими бронями)? Блок «Сегодня в офисе · свободно» должен отражать реальную занятость?
- **В-9.** Входит ли организатор в число участников? Допустима ли бронь на одного человека?
- **В-10.** Есть ли утверждённые тексты ошибок? У какого поля показывать ошибку прошедшего времени и длительности?

**Контактные данные**
- **В-11.** Должна ли «рабочая почта» быть на корпоративном домене? Принимать ли кириллические домены? Есть ли ограничения длины?
- **В-12.** Какие символы и какая длина допустимы в имени?

**Результат бронирования**
- **В-13.** В каком формате показывать дату в сообщении? Нужно ли выводить число участников и почту?
- **В-14.** Нужно ли очищать форму после успешной брони? Что должно происходить при повторной отправке?
- **В-15.** Данные никуда не уходят. «Бронирование создано» — целевое поведение или заглушка до подключения сервера?

**Нефункциональные требования**
- **В-16.** Какие браузеры и устройства поддерживаются? Есть ли требования к доступности (уровень WCAG)?

### Допущения

- **Д-1.** «Сегодня» и «текущее время» определяются по часовому поясу браузера. Начало раньше текущего времени — ошибка.
- **Д-2.** Границы длительности включаются: 30 минут и 4 часа допустимы.
- **Д-3.** Встреча укладывается в одну календарную дату.
- **Д-4.** Количество участников — целое число.
- **Д-5.** Корректная почта — `локальная-часть@домен.зона`, без ограничения по доменам.
- **Д-6.** Эталоном считаются тексты ошибок текущей версии.
- **Д-7.** Формат даты в сообщении: допустимы ISO и ДД.ММ.ГГГГ.
- **Д-8.** Блок «Сегодня в офисе» декоративный.

### Проверенные области

- Все восемь правил раздела «Ожидаемое поведение»: позитивные, негативные и граничные значения.
- Дополнительно: HTML-инъекция в имени, некорректные адреса почты, снятие ошибок при исправлении полей, состояние после успешной брони, переход через полночь, даты в далёком будущем, мобильная ширина (iPhone 13), навигация с клавиатуры, разметка доступности.
- Встроенные календарь и выбор времени в Firefox (по опыту — частый источник проблем).
- Способ: ручная проверка — в Firefox 160.0; автотесты и скрипты Playwright — в Chromium 156, «сейчас» в них зафиксировано на 14.06.2030 12:00 МСК.

### Не проверялось

- Safari (WebKit).
- Реальное время около полуночи и часовые пояса, кроме московского.
- Экранные дикторы, контрастность, масштаб 200%.

### Риски

- При подключении сервера с BUG-01 и BUG-02 в систему попадут брони в прошлом, нулевой длины и на весь день.
- Вся валидация выполняется в браузере: без дублирования на сервере правила обходятся.
- BUG-03 станет хранимой XSS, если имя начнут сохранять и показывать другим.
- Автотесты зависят от доступности GitHub Pages; негативный тест сверяет текст ошибки дословно.
